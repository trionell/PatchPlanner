the inventory list · built · revision 5

The last card list

Everything else has been through the language. The catalog itself converged in Wave 5 — a panel, a category rail, a 308-row sheet — and the list you reach it from did not. It is still a stack of rounded boxes under a paragraph of explanation, with three ghost buttons on every row and two of the browser’s own dialogs behind them. design/audit.md says so in as many words: “the inventory list is the only card list left.”

P1 exempts it, and the exemption is correctly invoked — these are genuinely independent objects. Slice 30 wrote down what that is worth: a rule that correctly permits something is not a reason to keep it. So the question here is the one that rebuilt Events — not is this in violation, but what is this page for. It is for picking which catalog to open, and for knowing which one your shows are actually running on. The second question the page cannot answer at all today.

01 · the job

Which catalog, and is it live?

A catalog list is short — five rows, not five hundred — and it is opened for two reasons. Open the one I work in, which is a click on a name. And work out which of these five matters, which happens when last year’s price list is still sitting there, when a duplicate was made in October and never named properly, and when something needs deleting.

The second one is where the page fails, and it fails in a way the application already knows how to fix. An inventory’s identity is its use. DeleteInventory counts the events pointing at a catalog and refuses while any do — the number exists, it is authoritative, and today it is spent entirely on producing a 409 after you have already confirmed a native dialog. Owned gear settled this exact argument one wave ago: its Planned on column is, in the spec’s own words, “the only reason to open this page rather than the event you are working on”. Same number, same reason, other catalog.

So the redesign is not mainly a restyle. It is one column that has never been shown, wrapped in the frame the rest of the app already uses.

Frame
One PatchPanel: bar, content, strip. The panel title repeats the tab name above it, as patterns §1 requires — it is what anchors a surface that now has a top edge of its own.
Density
Navigation tier inside a panel frame, which is what Events does and is the honest answer to P2’s question: nobody scans five catalogs cross-referencing as they go. So text-sm rows at px-3 py-2.5, a text-xs sans header — and no micro-labels, no Pill, no striping. A 10 px mono header over five rows would be the sheet costume worn by something that is not a sheet.

The bar is the exception, and it is chrome. Revision 4 drew the primary button at size="sm", the navigation tier’s own, which put a 32px ＋ New catalog directly above a 28px ＋ Item on the sibling tab — the same control, in the same corner, one step apart. The bar now matches Owned gear’s exactly (size="xs", h-3.5 icon, the same search field), and the tier difference lives in the rows, where it means something.
The row is a link
Clicking anywhere in it opens the catalog — one click, because that is the page’s whole job. The Events unfold is deliberately not carried over: there, a row expands because the summary answers most of what you came for without the commitment of opening a show. Here the row already is the summary, and an unfold would be a second click in front of the only thing anyone came to do.
Searchnew
In the bar, in patterns §1’s fixed order — title, search, flex-1, the one primary action. Input size="sm" with the icon at pl-8, min-w-[12rem] max-w-xs flex-1: the same field Events and the catalog panel already carry, so the bar reads as the app’s bar at the first glance rather than the second. It matches name and source filename through matchesSearch — the same helper the other five surfaces use — which means 2025 finds the price list whether you named it that or the spreadsheet did.
Five rows, still
It is there before it is needed, deliberately: a control that appears once a list crosses some threshold is a control nobody has built a habit around by the time they need it. Over five rows it costs a field of chrome; over thirty it is the only way in. The cost is bounded and the benefit is not, so it goes in now.
Order
Alphabetical, unchanged (ORDER BY name ASC). Events earned a chronological spine because when is what you scan for; catalogs are scanned by name, and a list that reorders itself as usage shifts is a list you have to re-find your place in.
Strip
Same construction as every other panel’s: a top border, text-[11px], and a verdict rather than a repeat of the column headings. 2 unused is the line that tells you there is tidying to do. It redraws against the search — filtering to 2025 makes it read 1 of 5 catalogs · 291 items · not used by any event — because a readout that ignores the filter above it is answering a question nobody asked (patterns §4c).
04 · the columns

Five, and why each one is there

Catalog
The name, and the link. text-zinc-100 font-medium.
Items
Mono, tabular-nums, right-aligned — the app’s rule for a number a technician compares against the number above it. Already on the card today; now it arrives with the list instead of costing a request per row.
Categoriesnew
Quieter than Items, one step down in ink. It is how you tell a real catalog from a scratch one at a glance — 291 items in 12 categories is a price list; 3 in 1 is somebody testing the import.
Used onnew
The reason this section exists. The count of events bound to the catalog — the number the backend has always computed to guard the delete, shown before you reach for it rather than after. An unused catalog renders — in text-zinc-600, which patterns §5 reserves for empty and expected: nothing has been planned on it, and that is a fact, not a warning.
Source
Format then filename: LL price list, Generic, or hand-built. Not decoration — sourceFormat === 'll' is what gates the price-list export, so this column is the answer to “why does this catalog have fewer export buttons than that one”.
Not a Badge
The format is plain text. Badge and Pill tint database vocabulary values through lib/vocabularyTint (tokens §5); a source format is neither, and five chips down a five-row table would be colour spent on something nobody sorts by.

The frame
ui/Drawer as it stands, width="narrow" — the Buses width, max-w-md. Header px-5 py-4 with a text-lg title and a text-xs text-zinc-500 subtitle, body px-5 py-4 with the gap-5 the drawer owns, footer px-5 py-3 text-xs saying what the contents mean. Nothing overridden.
The interiorfixed
ui/GearList, which is what Rig, Buses and Universes are actually made of — and what revision 2 still had wrong, having drawn navigation-tier h-10 fields and text-sm labels inside it. A drawer’s frame is navigation tier; its contents are the work surface’s, because what is declared in here is referenced from a sheet: DrawerSection with a MicroLabel heading and a mono count, GearCard at px-2.5 py-2, GearSpecs at 10px mono, Button size="xs", Input size="sm".
Nothing is a field until Edit
GearTop’s rule — no form control ever appears here. The card states the catalog; the amber-edged GearForm below it is where the name becomes editable, in the one construction that also does create. The two specimens above are the same component with and without a card above the form.
Used on, as a section
DrawerSection label="Used on" count={9} of GearCards, which is the Universes drawer’s Models in the rig section in shape as well as in spirit: a list of the things that reference what you are looking at, each with its one value on the right in mono. Ordered chronologically, oldest first — the spine’s rule, because a list of shows should read the same way everywhere.
Every event, and no private scrollbar
The section lists all nine, and all forty when there are forty. It takes no max-h of its own: the drawer body is already flex-1 overflow-y-auto, so it scrolls when the contents outrun it. A capped section inside a scrolling body is the exact failure patterns §4 records against the category rail — twenty-seven categories cut off at the fold in a private scrollbar, on a surface with room to spare.
An event is a linknew
The whole card navigates to /events/{id}, closing the drawer behind it. Hover raises it to border-zinc-700 bg-zinc-800/40 and a text-zinc-600 → sits at the row’s end — the chain arrow’s own colour, and the shape that says this leaves the page. It renders as an <a href>, so it is a real URL: middle-click opens a show in a new tab, which is the point when you are checking which of nine to move off this catalog.
Over, not beside
It opens over the list, on a bg-zinc-950/70 scrim, which is why the row you were reading is still where you left it when it closes. Backdrop click and Esc close it; nothing renders when closed.
Two entry points
The ⋯ on a row, and a Manage button in the catalog panel’s own bar — so the rename you think of while looking at 308 items does not require going back first. One component, two callers.
Delete is absent, not disabled
P7’s reasoning, generalised past roles: a disabled control is a promise the interface cannot keep. A catalog nine events depend on cannot be deleted, so there is no greyed-out button and no dialog to dismiss — there is a section listing every show that holds it, each one a link you can follow and unbind. The 409 that used to deliver this news is now unreachable by anything but a race.
Delete asks in place
Inside the form’s own body, full width, in the notice construction Lighting’s address prompt established — never a dialog (patterns §2). The confirm is destructive; the control that opened it sits apart from Save, which is FormActions’ whole reason for existing.

08 · what it costs

One endpoint, four files, one document

Backendone query
GET /inventories gains three counts per row — itemCount, categoryCount, eventCount — as sub-selects in ListInventoriesForOwner. No migration, no new route. It removes N requests from the page it serves.
Why not derive it
Wave 4 refused an endpoint for Overview’s numbers because the browser already computed them; Wave 5 accepted one for the In use column because a COUNT over other people’s tables is something only the database can see. This is the second case exactly — and it is the same number DeleteInventory reads, so the count shown and the refusal that follows cannot disagree.
Frontend
pages/Inventories.tsx — InventoryList and InventoryRow replaced; a new components/inventory/InventoryDrawer.tsx built from ui/Drawer + ui/GearList; one line in the catalog panel’s bar for Manage; types/index.ts for the three counts. Nothing in components/ui/ changes — every primitive the drawer needs already exists, which is the test of whether this is one language or several.
Search costs nothing
Client-side, over a list already in memory: matchesSearch and a useState. No parameter, no request, no debounce. The same reason every other search in the app is client-side — the rows are all here.
Renaming the tabs
Two strings in pages/Inventories.tsx. The sidebar item, the header title and the route keep saying Inventories, because the page is the thing that holds both catalogs.
Gone
The last Dialog on desktop, both window.* dialogs, nine ghost buttons, three bg-zinc-850 cards, and the per-row listItems query.
design/
Same commit. audit.md records that the last card list is gone and that P1’s exception now has no instances — the rule stays, its worked example becomes a closed case. patterns.md §4c gains a sibling note: a panel may hold navigation-tier rows when the objects are few, which Events established and this confirms.

What the spec will say

One PatchPanel with a search field and five navigation-tier rows; Used on as the column this page has never had; ui/Drawer narrow for create, rename, duplicate and delete, opened from the row’s ⋯ and from the catalog panel’s bar; three counts added to GET /inventories; both window.* dialogs and the page’s last Dialog deleted; the tabs renamed Rental catalogs and Owned gear.

Deliberately not in it

No sorting and no column headers you can click — five rows in name order do not need it, and the day they do, that is the same day the search field earns its place twice over. No archive state: a catalog is used or it is not, and used on already says which, so a third status would be a flag to keep in sync with a fact. No default catalog for new events — the create form already picks the only one when there is only one, and choosing among several is a decision per show, not a setting.
