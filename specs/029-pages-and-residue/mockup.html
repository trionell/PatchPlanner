Design convergence · Wave 5 · mockup for approval

The pages, and what is left over

Eight surfaces outside the event tabs. The audit calls them “mostly already right” — navigation surfaces built with navigation-surface components — and for five of them that holds. Three do not: the inventory catalog is a 308-row work surface wearing a card stack, the vocabulary settings render nine cards where one panel would do, and the dashboard's headline number carries a badge that repeats its own label. This page draws those three, closes the radius ladder, and asks for one exemption.

02 · inventories

Three hundred and eight rows on the navigation tier

The sample catalog has 308 items in 12 categories, and every one of them is a px-3 py-3 row at text-sm. By P2's question this is unambiguously a work surface — it is the same list the rental order is derived from — and it is the largest table in the application by row count.

Around it are three cards: the category list, the item list, and, above both, a page header with the import controls. The category card does four jobs at once — it filters the item list, it renames categories, it assigns each category's planning picker role, and it holds its own add form — and the item card holds a fifth.

The rail only filters. Renaming a category, retyping it, deleting it and assigning its planning picker role all move into a Categories drawer. Today those four controls are stacked in the corner of every category tile, which is why only four categories fit on screen out of twelve — a filter you cannot see all of is a filter that does not work.

Import becomes a drawer, not a button and a green paragraph. It is the one operation on this page with something to explain: the server detects whether the file is an LL price list or a generic list, and today that is a title tooltip. The drawer holds the file picker, the blank-template download, the format note, and the result of the last import — which currently renders as a bare sentence above the layout and shifts everything down when it appears.

DMX modes move into the item's editor, in RowEditor's notice slot — the full-width block Wave 3 added for the address prompt. A mode belongs to an item; opening a dialog from a row to edit part of that row is the pattern the whole convergence has been removing. The sheet gains a Modes column so you can see which items have them without opening anything, which today takes twelve clicks.

The list view stays a card list — P1's stated exception, since each inventory is an independent object. It loses the “Create a new inventory” card, which becomes the page's one primary action, and each card gains its item count, so the size of a catalog is visible before you open it.

Each inventory is its own independent equipment catalog. Bind one to an event when you create it, and reuse it across events.

03 · owned gear

The same conversion, a fifth of the size

OwnedGearManager is the second tab of the Inventories page: one card, one always-open five-field form, one navigation-tier table of Item · Type · Owned · Notes · Planned on · actions. It converts to a panel with no rail — there is nothing to filter by — and it is the smallest piece of work in the wave.

The one column worth keeping exactly as it is: Planned on, which counts how many events have this item on their equipment list. It is a derivation (P6), it is why deleting an owned item can fail, and it is the only reason to look at this page rather than the event you are planning.

The stored value stops being a caption and becomes a column. It matters — it is what saved plans point at, and it is why renaming is safe and deleting is not — so it is shown once per row, in mono, where a column of keys lines up, instead of squeezed beside every label at 128 px and truncated.

In use is new, and it is the point. The backend already refuses to delete a value a plan references; the interface finds out by trying. Counting the references is the same derivation, made visible before the click needs an endpoint — the one piece of backend work in Wave 5, and it may be worth deferring. Without it the sheet is two columns and the notice says only that deletion may be refused.

One component, still two pages. Settings and My Defaults keep sharing it; the difference stays what it is today — which API the callbacks hit, and the sentence in the strip.

Three cards become one row divided by rules — P1 again: a gap between cards says these are separate, and three counts of the same account are not. The numbers go mono with tabular-nums, because they are numbers a person compares, and drop from text-3xl to text-2xl so they stop out-shouting the panel titles under them (P8).

The “Quick actions” card is deleted. One button and a sentence of marketing copy on the screen a user sees every working day. The button becomes the page's primary action, in the row with the page title, which is where the Events page already puts it. The role badge stays exactly as it is — it appears only when your role is not owner, which is a real signal.

Events barely changes. It is a grid of independent objects and P1 exempts it by name. It gains a search field, because twelve events fit and forty do not, and an actionable empty state — “No events yet” beside the button that makes one, rather than a sentence at the bottom of an empty grid. The introductory line of prose above the grid goes.

06 · login

One retyped button

Login is forty-seven lines and almost entirely correct. Two things in it are not, and both are P3's failure mode rather than a visual problem:

The sign-in control is an <a> carrying rounded-md border border-amber-500 bg-amber-500 px-4 py-2.5 text-sm font-medium text-zinc-950 — the primary button's classes, retyped. It is a link, so it cannot be a <button>; but a shared style that is copied instead of imported is exactly how the micro-label ended up with four definitions and two sizes.

And the error block is border-red-900 bg-red-950/50 where design/tokens.md §5 says border-red-800 bg-red-950/50. One step, invisible, and the sort of drift that is only ever fixed by someone grepping for it.

The fix is to let Button expose its class string — or to render an anchor through it with an as escape hatch — and to use the token. Nothing on the page moves. touches ui/Button This is the only change in either wave that reaches into components/ui/, and it is worth flagging for that reason alone.

07 · start page

The exemption

The Start page is the signed-out marketing page, built in Slice 20. It uses rounded-2xl cards, rounded-full chips, a rounded-[9px] brand tile, two radial-gradient grounds, a 44 px mono display heading and an animated dot travelling a cable path. None of that is in the design language, and none of it should be.

design/principles.md P2 lists “the start page” among the navigation surfaces, which is the only place the documents say anything about it, and that line is doing more work than it was meant to: it settles the page's density, and it has been read as claiming the page is inside the system. A landing page's job is to be memorable to someone who has never seen the product; the application's job is to disappear behind the patch. Those are different briefs, and one visual language cannot serve both without one of them losing.

What I would do instead of converting it: write the exemption into design/audit.md and design/principles.md explicitly — the signed-out marketing surface is outside this language; it shares the brand mark, the amber accent and the type families, and nothing else — and change exactly one thing on the page, the single rounded-lg on the feature icon tile, which is neither the page's own rounded-2xl nor the ladder's rounded-md and is therefore just a stray.

The alternative is to converge it: flatten the gradients, drop the display type to the ladder, and lose the patch-bay graphic. That is a real option and it would make the audit's grep come out clean. I do not recommend it — but it is the user's call, not the audit's, and it is the fourth ask below.

Seven of the eleven real uses are deleted rather than corrected, because they are the always-open form blocks the two waves are removing anyway. That is the useful thing this table says: A4 was never really a radius problem. It was a marker for a layout idiom — a bordered block of fields floating above a table — that the codebase reached for seven times, and the radius was how it showed up in a grep.

The lesson matches A12's, from Wave 2: a grep that matches a value finds instances, not the reason there are instances. The four genuine radius corrections are one-line changes; the seven that matter were a pattern.

09 · scope

What this wave does not touch

One possible endpoint, and it is optional. The In use column on the vocabulary sheet needs a reference count the API does not expose today. Everything else in the wave renders data already fetched. If that count is deferred, the sheet is two columns and nothing else changes.

One touch on components/ui/, on Button, so Login can stop retyping its classes. Wave 4 touches none. Both will be asserted by a diff.

Mobile keeps its own branches. Inventories, Events and the vocabulary cards all have isMobile paths rendering CondensedListRow lists and full-screen filter dialogs. The rail is a desktop construction — on a phone the category filter stays the dialog it is today.

Nothing about auth, roles or sharing. The read-only paths on these pages already follow P7: a viewer is passed no handler and sees no control.

Not done, deliberately: the inventory sheet is not sortable, there is no bulk edit and no bulk delete, and an item still cannot be moved between categories except by editing it. Import already handles the bulk case, which is how a 308-item catalog gets there in the first place.

10 · to approve

Four calls before the spec is written

1 · Inventories — a category rail, and two drawers

The categories become a filter column of the panel; renaming, retyping, deleting and picker-role assignment move into a Categories drawer; the import controls, the blank template and the last import's result move into an Import drawer; DMX modes move from a dialog into the item editor's notice slot. The list view stays a card list and gains item counts.

2 · Settings and My Defaults — nine cards become one panel

The same rail construction, its second use, with the vocabularies as the rail and the selected vocabulary's values as the sheet. The stored key becomes a column rather than a caption. The open question inside this one: is the In use count worth an endpoint? It turns “deleting may be refused” into “two channels use this”, and it is the only backend work in either wave.

3 · Dashboard — the badges go, and so does “Quick actions”

Three stat cards become one row divided by rules, with mono numbers and no chips; the recent-events list goes full width; Create event moves to the page's own action row and the marketing sentence beside it is deleted. Events keeps its card grid and gains a search field.

4 · The Start page — exempt it, or converge it?

My recommendation is to exempt it in writing: record in design/audit.md and design/principles.md that the signed-out marketing surface is outside this language and shares only the brand mark, the accent and the type families — then fix its one stray radius and leave the rest alone. The alternative is converging it to the ladder, which would make the audit's grep come out clean at the cost of the only page in the product whose job is to be memorable. This is the one ask where I think the audit, taken literally, points the wrong way.
