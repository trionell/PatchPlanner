OpenSpec change · equipment-item-picker · revision 2 · for approval

Fifteen rows in this catalog are called Mikrofonkabel

The add row's Item field renders <category> — <name> over 338 catalog rows in one flat list. Fifteen of those rows say Signalkablage — Mikrofonkabel and nothing else, because the thing that tells them apart — 0,5m, 7,5m, Tele-XLR hane — lives in a description field this application has never shown here. The Item field becomes a catalog you browse: a category rail, a search that reads descriptions, several items chosen in one visit, and the same description on the row afterwards so the line you added is the line you can still recognise. Source defaults to rented.

01 · the evidence · live

A name is not an identity, and this field has only ever shown the name

The Item field below is a real <select> carrying the real labels the application builds today — {item.category_name} — {item.name} for a rented item, {item.category_type} — {item.name} for an owned one. Open it and scroll to S. Fifteen consecutive entries are the same seventeen characters.

And the owned side of the same field, on this database, has nothing in it at all. owned_items has no rows, so today's source: 'owned' default opens the add row onto a picker holding one entry, reading Select item…. That is §02.

02 · settled

The default source is the catalog that has anything in it

EMPTY_ADD.source is 'owned' and the phone's useState(row?.source ?? 'owned') agrees with it. Both become 'rented'. This is not one of the two choices — it is decided, and it is drawn here only so the specimens in §§03–09 are all drawn from the same starting state.

Two consequences follow from it and neither is a new rule. The add row opens with Audio and Light rather than Qty, because that is what a rented line carries. And the option order does not change: owned stays first in the list. A default is a value, not a position, and reordering a two-item vocabulary to advertise the default is how a list stops being alphabetical for a reason nobody can find later.

03 · the field

A field that names what it holds instead of holding a value

The Item field stops being a Select. It becomes a control the width of the grow slot at ui/Button variant="outline"'s geometry — h-8 on the desk, h-10 in the hand — that is empty, that names the one record it holds, or that counts the several it holds. Pressing it opens the catalog. This is the building block design/components.md does not have, and §11 names it and says where it would be written.

The count is the whole of the many-case, because §06's batch block states all five names in full immediately below the field. Repeating them truncated inside 160 px would be the disease this change exists to cure.

Filled, it reads name in the sheet's own ink, then ·, then the description in the muted role — the same two facts in the same order the catalog row it came from puts them in. Where the item has no description the field says the name and nothing else: the em-dash the sheets draw stands in for a missing value in a column, which has to be occupied; a field with nothing to add says nothing rather than drawing a value that was never typed.

04 · the overlay · live

The catalog browse already exists, read-only, and this switches its rows on

EventInventoryBrowser is a ui/Drawer holding a ui/PanelRail of categories beside a SheetTable with a Description column. That is the surface this change needs, minus the ability to click a row. So the picker is the same construction with a search box added and onSelect passed — the fifth instance of patterns.md §4's rail, not a new pattern.

Try it. Click a rail row, type in the search box. Then either click a row's name — one item, drawer closed, done — or tick several and confirm. That is §06, and it is drawn live here because the two gestures only make sense against each other. The search matches name and description through lib/patchSearch's matchesSearch, which is the application's one matcher and already the one the Rental sheet searches descriptions with — so typing 7,5 finds one cable out of fifteen.

three columns
Item · Description · Stock, and every one of those three words is already a column heading on the Rental Order sheet. Nothing here invents a word. Stock reads quantity_available for a rented item and quantity_owned for an owned one: one column, two derivations, one claim — how many of these exist.
why Stock is there at all
Because the question this whole sheet answers is what is coming with us, and have I got enough of it. Choosing the 4m mic cable when the catalog holds four of them is worth knowing before you type 12 into Audio, not after. A stock of 0 is stated and never withheld or greyed — you may plan against an empty shelf, and the rental order's is_over_stock is what reports it, exactly as it does today.
no price column
The picker is planning. What a hire costs is the rental order's subject and it has a column for it there. A fourth column here would also cost the Description its width, which is the one this change exists to add.
no Category column
The rail beside it is the category — the same argument EventInventoryBrowser already makes in writing for the same rows. When the rail is on All items and a search spans categories, the rail row stays lit on All items and the count says 34 of 338, which is what tells you the result is not filtered.
picking
Two gestures per row — patterns.md §4's own rule, the one the canvas states as the label selects, the dot cables. The name chooses that item and closes. The tick adds it to a batch and keeps the drawer open. §06 is the whole of it, including what happens when both would apply. A chosen row takes bg-amber-500/[0.04] and a 2px amber left edge — the sidebar's own mark for this is the current one — so the state never rides on colour alone (P4, P5). Revision 1 said one click was the answer and no confirm existed. §06 overturns that.
already on the sheet
A row the event already has renders with no tick at all and states on the sheet · 8a — beside the name on a desk, where PanelRailRow already puts a qualifier, and in the row's trailing slot in a hand. Absent, never disabled — P7's own preferred shape, reaching a case that is about data rather than about a role. §06 says why re-picking is not merely redundant but destructive.
the search box
Sticky at the head of the rows, Input size="sm" on the inset ground, with a mono count of matches at the far end — the desktop tier's form of the sticky bar D4 already built for the phone. It is focused when the drawer opens, because finding is what the drawer is for.
the footer
None until something is ticked — with an empty selection this is the browse it always was, and there is nothing to confirm. Once anything is ticked it states “3 items selected · 3 lines on the sheet” with Choose 3 items at ml-auto. Revision 1 said the drawer took no footer. It qualifies now under that decision's own test: it states what the contents are and carries a count that changes while you work, which is exactly why the Rig drawer keeps its footer. Unchanged: what the drawer does is read once, so it stays info behind the i, under noteId="equipment-item".
05 · the two catalogs

Five fixed types and twenty-seven free-form categories are one rail, because a rail takes rows

The two catalogs group differently and this is the only place in the change where that shows. An owned item carries category_type, one of five reference values. A rental item belongs to a category record with a name of the inventory owner's own choosing and a category_type beside it. PanelRailRow already takes exactly label, qualifier and count, and it already renders both shapes — EventInventoryBrowser passes the qualifier, the Inventories page does not.

So neither catalog is branched on. Each derives the same row list, and the rail never learns which one it is showing. That is Constitution Principle II at the pixel: a component must not know a category's name, and here it does not know its shape either. A category with no items is not listed, because the list is derived from the items present — a user whose gear is all audio sees one rail row and not five, four of them zero.

rented 27 categories · 338 items

The rail scrolls on its own and is given no height of its own — PanelCols stretches it to the drawer body, which is §4's standing rule and the one a leftover max-h broke twice.

owned up to 5 types

No qualifier column, because on this side the label is the type. And three rows, not five: rigging and video are absent because this catalog holds none. The counts are invented — owned_items is empty in the database, which is §09's second state.

06 · choosing several

The quantities stay where quantities live, so the catalog stays a list you read

“That would be handy and save a lot of clicks and time.” The goal is fewer round trips through the overlay, so everything below is decided against that and not against a basket for its own sake. Adding six cables today is six opens, six scrolls and six saves. It becomes one open, six ticks, one save.

The hard question is the quantities: one Qty field, or one Audio+Light pair, cannot serve five items. There were three ways out and two of them are wrong.

not in the picker row
A number field per catalog row breaks patterns.md §2 outright: “Nothing in a sheet row is a form control. A cell that is permanently an <input> turns a scannable list into a form.” That is the lighting fixture table's own failure — thirteen columns and twenty-four live controls — and 338 rows is a worse place to repeat it. The tick is a selection state, not a value, which is why it is the one control a picker row gets.
not “fix it on the sheet”
Landing five lines at a default and correcting them afterwards trades five clicks in the overlay for five row-editor opens on the sheet. That is not a saving; it is the same work, moved, plus a moment where the plan states quantities nobody chose.
so: the add row becomes N rows
Choosing five closes the drawer and the editor grows a line per item, each with its own quantity, saved by one Add 5 lines. The picker stays a list you read; the quantities stay in the editor at the editor's own tier; and at N = 1 it is literally today's row — a micro-label over a control is what FieldStack already is.

where the quantity comes from
A chosen line lands at one, in the department its category names.
A rental order has two departments. A catalog category carries category_type — the rail already shows it as the qualifier — so lighting lands in Light and everything else lands in Audio. Owned lines land at Qty 1, which is what the single add already defaults to. This is P6 at the level of a default: a value that carries meaning is derived, not typed, and it is what makes the fast path tick five, confirm, save rather than tick five, fill in five fields, save. Every one is overridable in the block before saving.
what one item costs
Exactly what it costs today. Open the field, click the row's name, press Add line — three, the same three as the current select. The tick is the second gesture and it is the one that opts into a batch. The name's shortcut exists only while nothing is ticked: once you have started a batch, clicking a name ticks it, because closing on one would mean throwing the batch away. If those two gestures read as too subtle, the fallback is one gesture and a confirm — and then adding one item costs one click more than it does today. That is the trade, stated rather than hidden.
the two verbs
The drawer's confirm says Choose 5 items and the editor's says Add 5 lines, because they do different things and neither may claim the other's. Nothing is saved when the drawer closes. Items in the catalog, lines on the sheet — the sheet's own two words, kept apart.
no note in a batch
The single add keeps its Note field exactly where it is. The batch has none: a note is prose written about one line, and five note fields in an editor is a form nobody fills in. Notes are added afterwards by opening the line — which is one click on a row, and the same click at either width.
one batch, one source
A batch comes from one catalog, because the picker was opened onto one. Changing Source clears it — the same rule that already clears a single chosen item, applied to five. Mixing owned and rented in one add would also mean two different quantity shapes in one block.
the save
One action, N calls.
Both endpoints are already PUTs keyed on an item id — putEventOwnedEquipment and putManualRental — so a batch is a loop and needs no backend change.
Run in sequence, and do not stop at the first failure. Stopping early leaves the user guessing which half landed.
One invalidation at the end, not one per line.
when one of them fails
The editor stays open holding only what failed.
The three that succeeded are already rows on the sheet behind it. The one that did not is still in the block with its quantity intact.
The confirm re-reads Add 1 line, so pressing it again retries exactly the remainder.
This is patterns.md §7d's “a failed save keeps the sheet open with every value intact”, per line rather than per form.

A re-pick is an overwrite, not a duplicate

Both endpoints are PUTs keyed on the item id. Ticking an item the event already has and confirming would replace the quantity already planned, silently, with a derived default of 1 — and on a catalog of 338 opened for the second time, that row is right there in the list.

So a row the event already has carries no tick and its name does not choose. It states on the sheet · 8a beside its own name, which answers why can I not pick this with a fact rather than with a rule. It is absent, never disabled — P7's own preferred shape — and the row stays fully readable, because knowing you already have eight of them is exactly what you opened the catalog to find out.

Changing that line is the sheet's own row editor's job, one click behind you, which is where every other quantity on this surface is changed.

07 · the phone · live

A sheet over a sheet, which is not new — it is what every picker on this phone already does

ui/Drawer is a bottom ui/Sheet below 768 px, and the add form is already a ui/Sheet. So the picker is a sheet raised over a sheet — and the application has shipped that construction since ROADMAP D4: EventInventoryBrowser renders inside a drawer's sheet and its MobilePicker opens a second one. useEscapeToClose was given an overlay stack in that slice for exactly this, and its own comment names the case.

The resolution is a second layer, not a replacement. The add sheet stays mounted, so the draft — the note you typed, the quantity you set — is never unmounted and never lost. Replacing the add sheet's contents in place would mean a back control, a title that swaps and a navigation stack inside ui/Sheet, which has six props and no more, on purpose.

The two gestures survive the width, and they get more room here than they have on a desk. A picker row's body is the name — tap it for one item and the sheet closes. Its trailing slot is a 44 px tick target at the right edge, where the thumb already is — tap that for a batch. CondensedListRow's trailing takes one state or one affordance, never both, and this is that rule predicting its own cases: a row is either addable, and shows the tick, or already on the sheet, and shows so.

Try it. Tap the Item field in the left phone. Tap a row's name for one item, or its tick for several and then the confirm. You come back to the add sheet with the field filled and the note still there.

This is the one place the rule as written does not settle it, and §11 says what approving A would have to add to design/.
the bar has two rows
D4's sticky bar is a category picker and a count. This one adds a second row holding the search field, open rather than behind a target. §7b's rule — search is a target, not a field — is justified by a field that “costs 44 px on every screen to serve something done on some of them”. A deliberate departure, with the rule's own justification as the reason it does not apply, and the first thing §11 flags.
the category picker

the row
CondensedListRow, unchanged: min-h-[44px], leading-tight, both lines truncating. 08 · the keys

One Escape must not cancel two things, and where the overlay is rendered decides it

RowEditor binds Escape to discard the whole add and ⌘↵ to save, as a React onKeyDown on the editor's own element. ui/Drawer binds Escape to close itself, through useEscapeToClose's window listener. Both fire on one key press — and the second one costs the user everything they typed.

The window half is already solved and the drawer wins it: the stack fires only its top entry. The half that is not solved is the React half, and it is not a bug in either component — React's synthetic events bubble along the React tree, not the DOM tree. A drawer rendered inside <RowEditor>'s children is fixed inset-0 in the document and still a child to React, so a key pressed inside it arrives at the editor's handler.

the rule this change would add
An overlay opened from inside a row editor is rendered beside the editor, never within it.
One line of placement, no new prop, no stopPropagation anywhere, and it holds for ⌘↵ as well as for Escape. It belongs in patterns.md §2, beside the editor's other standing rules.
AddEquipmentLine() // WRONG — the drawer is a React child of the editor, so Escape // closes the drawer AND discards the add. <RowEditor onKeyDown={…}> …fields… <Drawer open={picking} …/> </RowEditor> // RIGHT — a sibling. The editor's handler never sees the key. <> <RowEditor onKeyDown={…}>…fields…</RowEditor> <Drawer open={picking} …/> </>
drawn · the whole of the collision, and the whole of the fix
the two-step out
Escape with the picker open closes the picker. Escape again discards the add. Two presses for two things, which is what the keys line under the editor already promises for the second one.
focus
Opening the drawer focuses the search box. Closing it — by choosing or by Escape — returns focus to the Item field, so Tab continues into Audio and ⌘↵ lands on the editor that raised it. ui/Sheet already stores its return target; ui/Drawer does not, and this change is where it would.
from the keyboard alone
The rail rows are <button>s and a picker row carries a real <input type="checkbox"> beside a named target, so Tab reaches both and Space ticks while Enter chooses. Nothing here needs a roving tabindex or a listbox role: it is a table of records with a selection, and it should read to a screen reader as one.
and the batch's confirm
⌘↵ inside the editor saves the whole batch, which is what it already means — save this editor. It does not save one line and move to the next, because a batch is one add.

no matches
Names the query and the filter that is on, because the filter is the likelier cause — and offers the widening as a control rather than as advice. With the rail already on All items the second half and the button both drop, leaving No item matches “7,5”.
an empty catalog still opens
The field does not go dead and does not disable itself. A control that refuses to open explains nothing; a drawer that opens onto one sentence and a route explains everything. That is P7's argument — a disabled control is a promise the interface cannot keep — reaching a case that is about data rather than about a role.
in flight
Loading catalog…, never Nothing in this catalog yet. Both queries start cold the moment the drawer opens, so the empty sentence would otherwise be the first thing every user of a full catalog reads, every time, for one round trip.
a long description
Truncates at the column with a title, exactly as the browse and the rental sheet already truncate theirs at max-w-56. The longest real one is Kondensator med klämma för slagverk at 34 characters, which fits.
an absent description
In the picker's Description column: an em-dash, because a cell must occupy its column. In the phone row's subtitle: dropped, because a subtitle is a join. In the record field: nothing, because a field states what it holds. Three answers, one rule — and all three already exist in the code.
everything already added
Not an empty state. A category whose every item is on the sheet still renders every row, each stating on the sheet · N, because that is the answer to what you came to look up. A list of things you cannot pick is not the same as no list, and the footer simply never appears.
discontinued items
Already excluded, server-side, by the endpoint the picker reads. No new rule, and no new filter control — stated only so nobody adds one.
10 · reading it back

A picker that tells two items apart, feeding a sheet that does not, is half a fix

§§03–09 fix choosing. On their own they do not fix reading back: the Equipment sheet's Item cell renders row.name and nothing else, so two lines added from two different mic cables land as two rows reading Mikrofonkabel · rented · Signalkablage, differing only in a number. On a phone they are two CondensedListRows with the same title and the same subtitle.

And the same line already reads correctly one tab away. RentalSheet has had a Description column since Slice 28 and searches it. Equipment shows the same rented line without it. That is one surface disagreeing with another about what a line is called — which is the condition design/ exists to stop, and it is why this is in scope rather than beside it.

11 · the cost to the language

Three things get written into design/, and none of them is drafted here

The alternative that is not being built, recorded in one paragraph so the reasoning survives: keep the <select>, wrap each category in an <optgroup> and append the description to the label. It is about fifteen lines, adds no component and touches design/ nowhere. It answers the description completely and the clumsiness not at all — still 338 rows in one scroll, no search, no category filter, no stock (the label has no room for a third clause; iOS cuts the wheel near thirty characters), no empty state, and a popup the operating system owns, which no token in this language can reach. The complaint had two halves and it answers one.

What approving this writes into design/

1 · A new component, in components.md §4 (shared components), beside ui/Input and ui/Select: ui/RecordField. A control that stands for what it holds rather than for a typed value — empty it invites, holding one record it names it and its qualifier, holding several it counts them, and it opens whatever overlay the caller passes. h-8 at the work tier and h-10 in the hand, which are the two heights every other control in that section already takes. §4 and not §5, because it is one control at both reaches rather than a phone composition. Revision 1 wrote this as “names a chosen record”; the many-case widened it.

2 · A fifth instance in patterns.md §4 — “The filter rail, as the fourth” becomes the fifth. The picker is not a new pattern: it is ui/Drawer flush + PanelCols + PanelRail + SheetTable, which is the read-only browse, plus a search row, a tick and a selection footer.

3 · Two sentences in patterns.md §2. An overlay opened from inside a row editor is rendered beside the editor, never within it (§08). And a row editor may hold N lines under one confirm, where the lines were chosen together and differ only in a quantity — the batch block being a full-width child of the editor's own flow, at N = 1 the editor it already is.

And two clarifications the language does not currently carry. First, §ui/Dialog's interrupts vs accompanies test does not separate this picker from the cable pickers that are Dialogs — both are one choice raised mid-form. The distinction proposed here is how much work happens inside: a vocabulary of eight cable types is answered; a catalog of 338 across 27 categories is worked in, and the read-only browse of these exact rows is already a Drawer on that reasoning. The multi-select makes this more pressing, not less — an overlay you tick five things in is not an interruption by any reading. Second, patterns.md §7b's search is a target, not a field gets a stated exception for a surface whose sole job is finding rows (§07). Neither has been ruled on, and neither is drafted here. The design is approved first and written second.

12 · scope

What this deliberately does not do

no inline combobox
A type-to-filter field in the Item slot was ruled out before this document and is not drawn, not suggested and not kept as a fallback.
no note in a batch
§06. The single add keeps its Note field; five of them is a form nobody fills in. Notes are written afterwards, by opening the line.
no batch across both catalogs
§06. One picker, one source, one quantity shape. Changing Source clears the batch, which is the rule that already clears one chosen item.
no re-pick of a line you already have
§06. Both endpoints are PUTs keyed on the item id, so a re-pick is an overwrite. The row states on the sheet · N and carries no tick.
no batch delete, no batch edit
The batch exists only while an add is open. Once the lines are on the sheet they are rows, edited one at a time, which is patterns.md §2's standing rule and is not reopened here.
no recents, no favourites
Both are stored preference for a problem search has not been given a chance to fail at. If finding is still slow after this ships, that is evidence and this is where it would go.
no create-from-picker
You cannot invent a catalog item from inside the picker. A catalog is declared once and referenced often — §3's own words — and it is declared on the Inventory page.
the sheet's own search gains one field
§10. Find a line… matches the description too, which is what the Rental sheet's already does. Nothing else about it changes.
no price anywhere in the picker
§04. Planning here, pricing on the rental order.
an existing line's item stays fixed
§03. Moving a line across catalogs is a delete and a create, which the editor has refused to call an edit since Slice 28 and still does.
no grouped native select
§11 records it as the alternative considered, in one paragraph, and it is not being built.
nothing in design/ has been edited
§11 lists the three things this would add and drafts none of them. The design is approved first and written second.
